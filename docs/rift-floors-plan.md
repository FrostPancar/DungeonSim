## 1. The short version

Today a delve is a list of rooms resolved off-screen, one every 26 ticks. The "campaign view" just draws that list. You pick a party and a stance, then watch.

After this change, each **Rift floor is a real map**, like the camp. It has its own `World` (terrain, features, buildings), its own monsters, wildlife and ground items. Colonists who go through the gate **stand on that map**. You select them, right-click to move, mine, harvest and fight, and they eat, tire and haul, all through the same code the camp uses. Floors are smaller and simpler than the camp map, but they're dressed for their biome: seams and crystals, fungus and herbs, ruins, cages, chests and altars, and whatever lives there. Monsters are placed when the floor is generated. Stairs lead deeper.

| | Today | After |
|---|---|---|
| **Delve** | Room list, auto-resolved | A tile map per floor, played directly |
| **Control** | Stance and party pick only | Same as camp: select, right-click, work orders, squads |
| **Enemies** | Rolled per room, fought in one resolver call | Placed on the map at generation; they patrol or guard, and contact starts a fight |
| **Loot** | Tallied into `exp.loot` | Real items on the ground or in chests, carried or hauled up the stairs |
| **Depth** | `roomCount` rooms | Floors 1…N, each with stairs to the next, deeper floors harder |

## 3. Architecture: more than one map

**The key idea:** colony code already works on "whatever `game` it's handed", so a floor can be a *scoped view of the game*:

```js
// A Site is one playable map. The camp is sites[0]; each Rift floor is another.
// As built: `game.maps[]` (the camp is maps[0]) and `c.mapId`, because `game.site` already names the
// overworld colony location. Map-local fields are accessors on Game.prototype onto `this._m`.
site = { id, kind: 'camp' | 'floor', depth, biome, world, raiders: [], beasts: [], ground: [], jobs: [], occ, siteWork, rushed, unreachable }

// Ticking a site: a view whose map-local fields point at the site,
// and whose everything-else falls through to the real game.
const view = Object.create(game);
Object.assign(view, { world: site.world, colonists: site.colonists, raiders: site.raiders, beasts: site.beasts, ground: site.ground, jobs: site.jobs, … });
for (const c of site.colonists) tickColonist(view, c);
```

Resources, research, rng, log, stats and bonuses are shared by the whole colony, so they're read through the prototype. Loot mined on floor 3 lands in the same stockpile.

**The trap:** code that *assigns* a shared primitive (`game.overflow += n`, `game.jobsDirty = true`) would write to the view instead of the game. Phase 1 is an audit of every `game.X =` in the sim modules, sorting each field into map-local (it belongs on the site, so writing to the view is correct) or colony-wide (route it through a setter, or turn it into an object field). A test runs a floor tick and checks that no own properties show up on the view except the known map-local ones.

- `game.colonists` stays as the **roster of everyone**. Each colonist gets `c.site` (a site id). The view's `colonists` is the per-map list, so "who is nearby" logic stays local.
- `game.world` keeps pointing at the camp, so existing callers and tests don't change.
- `c.away` stops meaning "in the Rift". A colonist on a floor is present, just on another map. The meaning of `away` narrows to "off-map entirely" (caravans, the overworld).

This keeps the camp code as-is. Anything that works in camp works on a floor because it *is* the same code.

## 4. Generating a floor

`generateFloor(rng, biomeId, depth, riftLevel) → World` in a new `src/floors.js`. It reuses `World`'s layers, but not its overworld terrain generator.

**Size:** 40×30 on floor 1, growing about 10% per depth, capped at 64×44. The camp is 72×50, so floors are smaller and quicker to cross.

**Shape** comes from the biome's `layout` style, which maps onto a carve algorithm:

| Layout | Carve |
|---|---|
| `warren` | Drunkard-walk tunnels, many small chambers |
| `hub` | One big central cavern with spokes |
| `fortress` | Rectangular rooms and corridors, with **pre-built walls and doors** (real `building` entries, so they block, burn and can be smashed) |
| `cave` / default | Cellular-automata caverns, smoothed, with the largest region kept |
| `linear` | A long winding main path with side pockets |

Solid rock is `T.ROCK` and is mineable, the same as in camp. You can dig your own route.

**Dressing:** a pass per biome, all taken from the biome's existing `BIOMES_RIFT` entry:

- **Minerals:** the biome's mining `nodes` become veins in the rock (existing `FEATURES` with `inRock`), denser deeper down. A crystal/arcane vein feature is added for magic biomes.
- **Plants:** farming and woodcutting `nodes` become `FEATURES` on open ground: mushrooms, herbs, timber. Harvested with the same designation and job.
- **Structures:** `structures` (chest, cage, rack, nest, altar…) become new **Rift props** in `BUILDINGS` with `cat: 'rift'` that the player can't build. Chests hold rolled `rollLoot`, cages hold a prisoner (a recruit or a trapped beast), nests spawn wildlife, altars give a shrine buff.
- **Terrain:** biome water, chasm, lava or ice, reusing `T.WATER` / `T.CHASM` plus one or two new terrain rows if a biome needs it (web, ooze).
- **Light:** floors are dark. `drawLighting` runs at night strength on floors all the time, and glow features and props are light sources. Torches become worth building.
- **Stairs:** a `stairs_up` next to the arrival point and a `stairs_down` far from it (on the last floor, a **lair** instead: a walled boss room).

Everything is seeded from `game.rng.fork('floor' + riftLevel + depth + dawn)`, so a floor is deterministic and headless-testable.

## 5. What lives on a floor

| Thing | Source | Behaviour |
|---|---|---|
| **Monsters** | `rollGarrison(rng, biome, faction, tier, size, boss)`, the existing roller, placed as groups in chambers when the floor generates | New `guard` state: they hold their chamber and wander a little, then go hostile when a colonist comes within sight (6 tiles, line of sight on the terrain). They use the camp's raider movement code once they're hunting |
| **Wildlife** | Biome animals (new small `riftFauna` list per biome, drawn with existing `ANIMALS` sprites plus a few new grids) | Same as camp beasts: they graze and flee, some can be tamed and led home, aggressive ones act like monsters |
| **Ground loot** | A few `ground` piles per floor, plus whatever the chests hold | Hauled like camp items (see §8) |
| **Traps** | `rollTrap` | A hidden tile. The first colonist to step on it rolls the existing trap check; a successful survival check reveals traps within 3 tiles |
| **Prisoners** | `cage` props | Break the cage (a work order), and the prisoner joins or leaves by the existing hostility meter |

## 6. Going in, going down, coming back

- **In:** by day, select colonists and right-click the Rift Gate (or keep the party builder). They walk to the gate and step onto floor 1's `stairs_up`. No more "a party of five": anyone can go, with no cap. Livestock marked `delveReady` follow their handler.
- **Down / up:** right-click stairs to use them. The squad goes together and forms up at the other end with `formationTiles`, as it does today.
- **Out:** walking back up floor 1's stairs puts them back at the gate in camp.
- **Dusk:** the gate opens and the wave comes out. People on floors **stay on their floor** (see decision 2). The camp fights with whoever is home, the same as today, sized against actual defenders.
- **Dawn reshape:** today the interior reshapes every dawn. With real maps that would wipe a floor people are standing on. Proposal: **a floor reshapes at dawn only if nobody is on it.** A floor with people on it persists until they leave (see decision 1).
- **Level-ups** (every 4 days) apply to newly generated floors.

## 7. Fighting on a floor

Same as camp: **contact starts an encounter, and `resolveSiege`'s `simulateCombat` resolves it**. The only change is scope. Today a contact resolves *the entire wave* against *all defenders*. On a floor (and in camp from then on) it resolves the **local skirmish**: the hostile group that made contact, plus any colonists within 6 tiles of them. Two squads fighting two groups on opposite sides of a floor are two separate fights.

- The biome's `env` rules (cramped, fortified, elemental multipliers) go into `ctx`, the same as `resolveRoom` does today, so biome identity carries over.
- The combat core (rows, statuses, abilities, class trees) doesn't change. It's the same `simulateCombat`.
- Right-click an enemy with a squad selected: they close in (already built in part 1 of this session), and contact starts the fight.
- Downed colonists fall where they stand. Others can carry them (a new `rescue` work order) or leave them. Deaths are permanent, as they are today.

*A real-time, per-hit tile combat system would be a separate, much larger project. Only the scoped skirmish is proposed here (see decision 3).*

## 8. Loot and hauling

- Mining, harvesting and opening chests drop items on the floor's `ground`, using the same `dropItems`.
- **Carrying:** each colonist has a pack (`c.carry`, capacity from strength, plus pack beasts). Hauling on a floor fills packs instead of a stockpile. Items reach the colony stockpile when the carrier walks up floor 1's stairs.
- **Stairs cache (optional):** a buildable `rift_cache` next to floor 1's stairs that haulers can fill, then emptied from camp.
- Essences, trophies and bestiary entries are credited on the kill, as they are today.

## 9. Rendering and UI

- The renderer draws **one site at a time**: `renderer.site`. Camera position is remembered per site.
- **A site switcher** replaces the campaign-view button: a row of chips above the colonist bar (`Camp · F1 · F2 · F3`), each with a head count and a red dot when a fight is on. Hotkeys: `Tab` cycles, and clicking a colonist portrait jumps to their site.
- The colonist bar groups portraits by site.
- Alerts gain a site tag ("⚔ F2: Myrmiel's squad is fighting").
- The hover cards, inspector, orders, hourglass, progress bars and order lines from part 1 all work on a floor unchanged, because they read from the rendered site.
- The Rift drawer shows the floor list (depth, biome, explored %, who's there) and the level and rank climb it shows today.
- `drawCampaign` and the campaign view are removed once floors can be rendered.

## 10. What happens to the old expedition system

`expedition.js` still holds useful pieces: `awardXp`, belts and potions, `openStructure`, `harvestYield`, `applyInjury`, `finishExpedition`'s return summary. Those get reused. The room-by-room auto-resolver (`tickExpedition`, `resolveRoom`, `buildRoute`) is retired, along with autoplay's delve driver, which gets rewritten to send squads to floors.

**Tests and balance:** the integration sweep currently asserts a clear rate of 25–95%, survival over 60 days and a wave every night, all driven by autoplay delves. Those assertions need to be restated for floors. "Clear rate" becomes "floors reached / lairs killed". That's the riskiest part of the project, and it's why autoplay is its own phase.

## 11. Tests

- The floor generator is deterministic per seed; every floor has a walkable path from `stairs_up` to `stairs_down`/lair; every biome generates; sizes stay in bounds.
- The site view **leaks no colony-wide state**: after a floor tick, the only own properties on the view are the whitelisted map-local ones.
- A colonist on a floor eats, sleeps (on the ground), mines and hauls into their pack.
- Guards wake on sight, and a skirmish only involves nearby units.
- Stairs move a squad between sites, and walking out delivers the carried loot.
- The dawn reshape skips occupied floors.
- The existing 449 assertions stay green through phases 1–2. The sweep is restated in phase 5.

## 12. Build phases

| Phase | What | Playable after? |
|---|---|---|
| **1. Sites** | `Site` object, scoped view, `c.site`, state audit, camp becomes `sites[0]`. No gameplay change | Yes, identical game |
| **2. Floors** | `floors.js` generator (5 carve styles, biome dressing, stairs), renderer draws any site, site switcher | Yes: floors can be visited and walked, with no enemies yet |
| **3. Life** | Monsters with guard/hunt, wildlife, traps, chests and cages, skirmish-scoped combat | Yes: real delving |
| **4. Loot & return** | Packs, stairs delivery, rift cache, dawn-reshape rules, night interplay | Yes: full loop |
| **5. Retire & rebalance** | Remove the room resolver and campaign view, rewrite the autoplay driver, restate the sweep, balance pass | Yes: done |

Each phase ends with the suite green and a playable build.

## 13. Decisions I need from you

1. **Floor lifetime.** (a) A floor persists while anyone is on it and reshapes at the first dawn it's empty *(recommended)*; (b) floors are permanent until the Rift levels up (every 4 days); (c) always reshape at dawn and pull anyone still inside back to the gate.
2. **Night.** When the gate opens at dusk, should people on floors (a) stay put, while the wave hits the camp *(recommended: you split your forces on purpose)*; (b) get pulled out to defend; or (c) face a surge of monsters on their own floor too?
3. **Combat.** (a) The contact-triggered skirmish using the existing resolver, scoped to nearby units *(recommended: same feel as camp today)*; or (b) a new real-time, tile-by-tile combat where each unit attacks on its own. Option (b) is a separate project about the size of this one.
4. **Party cap.** Drop the five-person limit and let any number go down *(recommended)*, or keep five?
5. **Floors per level.** Floor count = Rift level (so level 1 is one floor and level 8 is eight) *(recommended)*, or a fixed 3–5?
